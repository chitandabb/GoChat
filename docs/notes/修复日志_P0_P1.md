## 2. P0-1：认领消息的退出路径记账闭环

### 改动文件

- `internal/service/chat/kafka_server.go`
- `internal/service/chat/kafka_server_test.go`（新增）

### 关键改动

- 新增 `skipClaimedMessage`：坏 JSON、误入文本批量的非文本类型等永久失败输入统一执行“置 done、清除 in-flight、`commitSafe` 提交”，不再 `continue` 后冻结分区水位。
- `consumeLoop` 在进入 Transmit 前先解析 Kafka 消息；JSON 解析失败不再进入既不落库也不重试的 Transmit 路径。
- `persistBatch` 的批量构建期和逐条回退期都覆盖坏 JSON、非文本类型；批量成功只提交真实完成的文本消息，不把被跳过的消息重新混入提交集合。
- Audio/Video 归属明确：满足 `PROXY + start_call/receive_call/reject_call` 的信令落库，保留 `AVdata` 并写入 `kafka_key`；SDP、candidate 以及其他不满足持久化条件的信令继续转发，但跳过落库并完成 Kafka 提交；落库失败仍进入重试队列。
- 增加提交和 done 标记的测试替身，使单元测试不依赖 Kafka Broker 或 Redis。

### 验证

- `go test -race ./internal/service/chat`：通过。
- 新增 `TestPersistBatchMalformedJSONClearsInFlightAndCommits`：坏 JSON 不进入失败重试，分区 `in-flight` 集合最终为空，提交记录包含该分区 offset。
- 坏 JSON + 正常消息回归：向 `chat_message` 投递 1 条坏 JSON，随后 ORDER 场景发送 5 对 × 200 条；接收端 `1000/1000`，发送端回显 `1000/1000`，重复、乱序、缺失均为 `0`。
- 坏 JSON 日志记录为“解析失败”后“跳过并提交”，`chat` 消费组各分区 LAG 均为 `0`，本轮没有“重复消费跳过”风暴。

## 3. P0-2：下行发送竞态与持锁 panic

### 改动文件

- `internal/service/chat/server.go`
- `internal/service/chat/client.go`

### 关键改动

- `push` 增加 `defer recover` 和非阻塞 `select`，将 `SendBack` 已关闭竞态视为本次发送失败，panic 不再逃逸到分发循环。
- 登录欢迎帧也复用 `push` 安全路径。
- 所有 `Server.mutex` 区间使用 `defer Unlock`；Clients map 只在锁内取快照，实际 `push` 移到锁外，避免连接关闭、慢客户端回收等可恢复调用持锁执行。
- `Client` 增加 `dropMu`，保护 Kafka 推送循环与 Server 分发循环并发调用时的 `dropCount`。
- `ClientLogout` 按 channel/Kafka 模式选择正确的 Server，锁内读取在线连接，锁外发送登出和关闭 TCP 连接，消除在线 map 并发读写。
- 群成员缓存的数据库回源移到缓存互斥锁外；锁只保护缓存检查和写入。
- 顺手修复 `normalizePath` 找不到 `/static/` 时的切片 panic，以及 Kafka Transmit 中坏 JSON、缺少 `receive_id`、未知类型的明确提交路径。

### 验证

- `go test -race ./internal/service/chat`：通过，无竞态报告。
- `SLOW -n 100 -burst 1000`：慢客户端 1.57 秒内断开；正常客户端业务消息 `1200` 条；正常客户端异常断开 `0`。
- SLOW 日志和当前 `logs/gochat.log` 检索无 panic、无“下行推送失败”、无分发循环 panic。
- Kafka 进程在 ORDER、SLOW、CHAT、GROUP 压测后持续存活，最终采样 WorkingSet 约 52MB，无进程退出。

## 6. Kafka 回归数据

| 场景 | 实测结果 |
| --- | --- |
| ORDER 50 对 × 200 | 接收端 `10000/10000`，回显 `10000/10000`，重复/乱序/缺失均 `0`，7.5s 收满 |
| 坏 JSON + ORDER 5 对 × 200 | 接收端和回显均 `1000/1000`，重复/乱序/缺失均 `0`，chat LAG `0` |
| CHAT 100 对 × 10 msg/s × 30s | 发送 `29354`，回显 `29354`，丢失 `0`，异常连接 `0`，P50 `103.9657ms`，P99 `743.3865ms`，max `838.2532ms` |
| GROUP 400 人 × 20 发言 × 50 | 预期/实际 `400000/400000`，送达率 `100.00%`，每成员 `1000/1000`，零送达成员 `0` |
| SLOW 100 正常 + 1 慢客户端 × 1000 | 正常业务帧 `1200`，异常断开 `0`，慢客户端 `1.57s` 内断开 |

`chat` 主消费组在回归后各分区 LAG 均为 `0`。`chat_push` 当前实现按 64 条批量显式提交，低于 64 的尾批会等待下一批，因此 Kafka 组描述中可能短暂看到尾差；本轮业务推送已全部被客户端收到，未将该既有 push 尾批提交行为误记为 P0-1 的 chat 消费失败。
