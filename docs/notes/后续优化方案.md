# 后续优化方案

## 1. 用户体系

### 1.1 手机号唯一约束

- 当前 `user_info.telephone` 在业务层会检查是否重复，但数据库层只有普通索引，没有唯一约束。
- 后续建议直接在数据库层增加唯一索引，避免并发注册或脏数据写入时出现重复手机号。
- 这是账号体系里比较基础也比较重要的一条约束。

建议方向：

- `telephone` 改为唯一索引
- 同时保留业务层的重复校验提示

### 1.2 邮箱唯一约束

- 当前 `user_info.email` 更像资料字段，没有唯一约束。
- 如果后续要做邮箱绑定、邮箱验证、邮箱找回密码、邮箱登录等能力，建议邮箱也加唯一约束。
- 除非未来明确支持“一人多邮箱”或“邮箱不作为身份要素”，否则唯一更合理。

建议方向：

- 若邮箱参与身份认证或安全验证，则改为唯一索引
- 若只是选填资料字段，可先保持可空，但要明确后续产品定位

### 1.3 密码加密存储

- 当前密码是明文存储，并且登录时直接做字符串比较。
- 这是必须尽早处理的安全问题。

建议方向：

- 改用 `bcrypt` 等哈希方案
- 登录时改为哈希校验
- `password` 字段长度同步调整，不能继续使用当前偏短的定长设计

### 1.4 在线状态轨迹落地

- 当前表中已经有 `last_online_at` 和 `last_offline_at`，但实际业务链路中基本没有真正写入。
- 后续可以把它接到登录、登出、断连等时机，用于后台管理和账号治理。

建议方向：

- 登录成功后更新 `last_online_at`
- 主动登出或连接断开时更新 `last_offline_at`
- 管理员后台支持查看长期未登录用户
- 未来可结合定时任务自动禁用长期沉默账号

### 1.5 邮箱能力扩展

- 当前邮箱只用于资料展示和资料修改。
- 后续可以扩成完整的邮箱安全链路。

建议方向：

- 邮箱绑定
- 邮箱验证
- 找回密码
- 安全通知
- 邮箱登录（按产品定位决定）

### 1.6 添加用户搜索方式优化

- 当前内部关联使用 `uuid` 是合理的，但直接面向用户使用 `contact_id/user_id` 作为添加入口不够自然。
- 后续应区分“内部关联键”和“用户搜索入口”。

建议方向：

- 用户搜索支持手机号
- 用户搜索支持昵称
- 用户搜索支持邮箱
- 如果以后偏企业场景，可继续扩展工号搜索
- 后端内部仍使用 `uuid` 做真正关联

## 2. 文件与资源存储

### 2.1 本地文件存储升级

- 当前头像和文件走本地文件系统存储。
- 这种方式适合本地开发和轻量部署，但不利于多实例和后续扩展。

建议方向：

- 后续考虑接入对象存储
- 私有部署优先考虑 `MinIO`
- 统一文件 key、访问 URL、上传链路

### 2.2 头像与文件访问链路标准化

- 当前数据库里保存的是本地静态资源路径或默认 URL。
- 后续可以把资源访问链路进一步收口。

建议方向：

- 统一上传服务
- 统一资源 URL 生成规则
- 数据库只保存稳定的资源标识或对象路径

## 3. 聊天与关系模型

### 3.1 群成员关系建模优化

- 当前 `group_info.members` 使用 JSON 存成员列表，轻量但扩展性一般。
- 群功能复杂后，查询、权限、统计都会比较难做。

建议方向：

- 后续可拆分独立群成员关系表
- 为群成员增加角色、状态、加入时间等字段

### 3.2 联系关系模型细化

- 当前 `user_contact.status` 承载了较多状态语义，包含好友、拉黑、群关系、禁言、退群、踢出等。
- 这种设计前期省表，但后期容易让状态语义越来越重。

建议方向：

- 后续评估是否拆分好友关系和群关系
- 或重新整理状态枚举，让语义边界更清楚

## 4. 接口与路由结构

### 4.1 统一接口前缀与版本管理

- 当前后端路由虽然在代码目录中使用了 `api/v1`，但真正暴露出来的 HTTP 路径并没有统一 `/api/v1` 前缀。
- 前端当前也是直接请求裸路径，例如 `/login`、`/group/createGroup`、`/contact/applyContact`。
- 这种方式在项目变大后，不利于做版本管理、接口分组、中间件分层和网关治理。

建议方向：

- 后端统一增加 `/api/v1` 顶层前缀
- 按模块使用 Gin Router Group 进行路由分组
- 前端统一请求 `/api/v1/...`
- 为后续鉴权中间件、管理员中间件、版本升级和接口下线预留结构空间

### 4.2 统一响应结构与错误处理

- 当前 controller 层大量手写 `c.JSON(http.StatusOK, gin.H{...})`。
- HTTP 状态码、响应体里的业务码、service 返回的 `ret` 各自承担一部分语义，但边界不够清晰。
- 目前存在较多硬编码：
  - 响应体直接写 `200 / 400 / 500`
  - service 内部直接写 `0 / -1 / -2`
  - 成功/失败提示文案直接写在业务代码里
- `BindJSON` 失败目前通常直接返回 `SYSTEM_ERROR`，没有把“参数错误”和“系统错误”区分开。
- 这会让 controller、service、前端协作时出现理解成本，也不利于后续做统一异常处理。

建议方向：

- 统一响应结构，例如 `code + message + data`
- 明确 HTTP 状态码和业务码的职责边界
- 把 `ret` 这类内部状态值收口为可读常量或错误类型
- 增加参数错误、鉴权失败、权限不足、资源不存在等细分业务码
- 统一成功/失败消息常量，减少业务代码里的文案硬编码
- 把请求参数绑定失败统一封装，避免每个 controller 重复写同一套返回

### 4.3 API 风格统一与 RESTful 化

- 当前项目整体接口风格偏 RPC，典型形式为 `POST + 动作型路径 + body 参数`，例如：
  - `/group/createGroup`
  - `/contact/applyContact`
  - `/session/openSession`
- 这种写法前期开发直接，但随着接口增多，资源边界、HTTP 方法语义、路径层级、批量操作规范会越来越不统一。
- 从学习和后续工程治理角度看，把接口逐步整理成更统一的 RESTful 风格是一个很有价值的优化方向。

建议方向：

- 统一按资源建模接口，例如 `users`、`groups`、`sessions`、`contacts`、`messages`
- 尽量使用 HTTP 方法表达动作，例如：
  - `GET` 查询
  - `POST` 创建
  - `PATCH` 部分更新
  - `DELETE` 删除
- 统一 query / path / body 的使用边界：
  - path 用于资源定位
  - query 用于筛选、分页、排序
  - body 用于提交复杂数据
- 对“通过申请”“拉黑联系人”“开会话”这类强动作接口，评估是保留动作型子资源，还是重构为更规范的资源状态变更接口
- 为后续 OpenAPI / Swagger 文档、权限治理、网关治理预留更标准的接口形态

学习价值：

- 有助于系统理解 Gin 路由、参数绑定、HTTP 方法语义、资源建模
- 有助于建立比“接口能用就行”更进一步的后端设计意识

## 5. 平台治理能力

### 4.1 举报与审核能力

- 当前已有管理员禁用用户/群的能力，但没有完整举报审核链路。
- 如果产品未来从轻量内部 IM 走向更开放场景，再考虑补足。

建议方向：

- 举报表
- 举报理由
- 审核记录
- 处理结果

## 6. 企业级认证与安全升级

### 6.1 补齐应用内鉴权体系

- 当前项目只有登录动作，没有真正完整的后端登录态鉴权体系。
- 前端主要依赖本地保存的 `userInfo` 维持“已登录”状态，后端对 `owner_id`、`uuid` 等前端传参信任较高。
- 这在正式产品里存在明显风险。

建议方向：

- 登录成功后签发 access token
- 配套 refresh token 机制
- 后端增加统一鉴权中间件
- 接口中的当前用户身份从认证上下文中获取，而不是完全信任前端传参
- WebSocket 接入鉴权，不再只依赖 `client_id`

### 6.2 企业统一身份接入

- 如果项目后续往企业版方向演进，建议不要只停留在“自己发 JWT”这一层。
- 更主流的企业做法是接入统一身份中心（IdP），把认证从业务系统中解耦。

当前优先建议方案：

- 接入 `Keycloak`

原因：

- 开源、自托管、成熟度高
- 支持 OIDC / OAuth2 / SAML
- 适合作为企业级单点登录与统一身份方案
- 适合后续扩展 MFA、组织角色、统一权限、审计等能力

建议方向：

- 以 OIDC 方式接入 Keycloak
- 后续支持 SSO（单点登录）
- 为 MFA / 更强认证预留接口
- 为组织、角色、权限治理预留演进空间

### 6.3 权限控制体系建设

- 当前项目基本没有完整的后端权限控制体系。
- 管理员相关接口目前更多依赖前端传参和业务约定，缺少统一的后端权限拦截与鉴权上下文。
- 后续如果走企业化路线，权限控制需要和认证体系一起补齐，而不是只做“是否登录”的判断。

建议方向：

- 第一阶段先补齐应用内权限控制：
  - 基于认证中间件识别当前用户
  - 将 `uuid`、角色、管理员标记等信息放入认证上下文
  - 为管理员接口增加统一的权限校验中间件
  - 不再直接信任前端传来的 `owner_id`、`uuid` 等身份字段
- 第二阶段逐步向企业权限模型演进：
  - 与 `Keycloak` 统一身份体系协同
  - 使用角色、scope、组织等信息进行粗粒度控制
  - 为后续更细粒度的资源权限、组织权限、审计留扩展空间

## 7. 当前优先级较高的优化项

现阶段优先建议记住这几项：

1. 补齐应用内鉴权体系
2. 密码加密存储
3. 手机号数据库唯一约束
4. 邮箱唯一约束（若后续参与认证）
5. 在线状态轨迹真正落地
6. 文件存储逐步升级到 MinIO 等对象存储方案
7. 后续接入 Keycloak 作为企业统一身份方案

## 8. 工程结构与依赖管理

### 8.1 从全局单例逐步过渡到显式依赖注入

- 当前项目大量依赖全局变量和包级单例，例如：
  - `dao.GormDB`
  - `config.GetConfig()`
  - `https_server.GE`
  - `gorm.UserInfoService`
  - `chat.ChatServer`
- 这种方式前期开发快，但随着模块增多，会逐渐带来耦合、测试困难、初始化顺序敏感等问题。
- 目前 service 更多是“通过全局变量自己拿依赖”，而不是由外部把依赖显式传入。

建议方向：

- 由 `main` 统一完成依赖装配
- service struct 显式持有 `db`、`redis`、`config`、`sms provider`、`logger` 等依赖
- controller 显式依赖 service，而不是直接引用包级全局实例
- 为后续单元测试、mock 替换、多实现切换预留空间
- 初期不必一次性全改，可以优先从用户、短信、鉴权等核心模块开始收口

优先级建议：

- 等整体项目阅读完成后，把“依赖注入 + 去全局单例 + 显式装配”作为首要工程化改造目标之一
- 这项改造适合作为后续鉴权体系、缓存抽象、短信实现替换、对象存储接入等能力升级的基础工程
