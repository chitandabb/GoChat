# 演示与部署环境说明（2026-08 实测）

本文档记录从"用户真实使用场景"出发走查后修复的问题、容器部署方式与演示步骤。
后端 `go build ./...`、前端 `npm run build` 均通过；容器环境已做全链路实测（见下）。

## 一、本地 / 容器启动方式

### 方式 A：Docker Compose（推荐，与生产形态一致）

```bash
docker compose up -d --build mysql redis kafka backend frontend
# 消息链路默认走 kafka：config.docker.toml 已设 messageMode=kafka
# kafka 宿主机端口为 29092（9092 常被其他项目占用，双监听器避让：容器网 kafka:9092）
```

## 一·二、2026-08-22 二轮走查修复（Kafka 化 + 前端成品化）

- **消息链路整体切 Kafka**：`config.docker.toml` 默认 `messageMode=kafka`；kafka 服务改双监听器
  （容器网 `kafka:9092` / 宿主机 `localhost:29092`，原广播地址 `localhost:9092` 会让容器内后端
  连到自己，docker 内 kafka 模式此前从未真正跑通）；backend 增加 `depends_on: kafka`。
  实测：topic 启动自动创建、e2e 19/19 全过、WS 收发经 broker（chat_message/chat_push offset 增长、消费组 lag=0）。
- **管理后台仿微信改版**：Manager 页换掉 Element Plus 默认风格（新 `manager.css` 与聊天端共用
  `--go-*` 令牌）；5 个管理表格统一头像+昵称+ID 列、`el-tag` 状态、选中计数、空选拦截、删除二次确认。
- **全局样式冲突**：chat.css 的 `.el-header/.el-footer !important` 全局覆盖收窄到 `.chat-container` 内
  （此前会把管理页头部顶成 74px）。
- **登录回车提交**：登录按钮移入 form 语义（`native-type=submit` + `@submit.prevent`），回车即可登录。
- **nginx 缓存策略**：`index.html` 禁缓存（`no-cache`）、hash 静态资源长缓存（`immutable`）——
  修复发版后老用户一直加载旧 bundle 的问题。
- **截图/GIF 全部重制**：7 张页面截图统一 1920x1080（新管理后台入镜），GIF 为 11s 实录
  （登录→会话→发消息→对方实时回复，经 Kafka 链路）。

## 一·三、2026-08-22 三轮走查修复（视口漂移 + 会话预览 + 管理员头像）

用户以小视口（约 1152x480）实测反馈 5 个问题，逐一复现并修复：

- **画面被"抛"上去、底部空白、滚轮漂移（根因）**：`.chat-wrap` 的两枚装饰光晕伪元素带
  负向偏移（`bottom:-16vw` 等），把 `overflow:hidden` 容器撑出约 184px 隐藏可滚动区——
  hidden 容器仍可被滚轮/程序滚动，一点就把整个应用顶上去；且光晕本就被全屏不透明的
  `.chat-window` 完全遮住，纯遗留死代码。修复：删除光晕；`.chat-wrap/.chat-window` 改
  `overflow:clip`（不产生滚动容器）；全局 `html/body` 锁 `overflow:hidden` + `height:100%`；
  登录壳 `AuthShell` 改壳内滚动兜底（`safe center` 防极矮视口裁顶）。
  实测（1152x480）：滚轮滚动/打开左下角"设置"菜单/发消息，窗口偏移恒为 0。
- **会话列表"暂无消息"**：后端会话列表本就不返回最近消息，前端只在收到 WS 时本地补。
  修复：`session/getUserSessionList`、`getGroupSessionList` 出参新增 `last_message` 预览
  （文本直出、文件按 MIME 折叠为 [图片]/[视频]/[语音]/[文件]、群聊非本人消息带
  "发送者："前缀），并按最近消息排序；预览**不进 Redis 缓存**（缓存只存会话名单，
  两条路径出参前现查），新消息后无需失效缓存。
- **会话/联系人列表排版错乱**：Element 的 `.el-menu-item` 默认 `line-height=菜单高度(≈56px)`
  被内层文字继承，"名字+预览"两行被撑成两个 56px 行框、列表项顶高到 102px 且文字错位。
  修复：两处列表统一压行高（名字 20px/预览 17px，项高 58/56px）。
- **联系人列表居中**：旧样式 `.contactlist-user-menu-item { justify-content:center }`。
  修复：联系人/我创建的群/我加入的群统一为仿微信行布局（头像+名称+ID 两行，左对齐）。
- **管理后台用户头像全空**：`/admin/getUserInfoList` 出参缺 `avatar/email` 字段（邮箱列也
  一直是空的）。修复：出参与服务层补齐两字段，前端表格零改动即恢复。
- 另发现并规避：浏览器缓存的旧 `index.html`（nginx 加 no-cache 前缓存）会把用户带回旧版
  bundle（如旧管理页）；带 `?cb=` 或强刷一次即恢复，no-cache 生效后不会再发生。

## 二、短信验证码（从用户场景出发的重点修复）

开发机 `configs/config.dev.toml` 里配置了阿里云 AK/SK/签名/模板（真实配置）。
容器环境（APP_ENV=docker）读取 `configs/config.docker.toml`，AK 为空。

**修复：两级降级策略（`internal/service/sms/auth_code_service.go`）**

1. `GOCHAT_SMS_DEV_MODE=true`（默认）→ 开发模式：验证码写入 Redis + 服务端日志打印
   （形如 `【开发模式】短信验证码 ... code=123456`），演示直接查日志取码即可，
   不依赖真实短信通道，也不花阿里云的钱。
2. `GOCHAT_SMS_DEV_MODE=false` 且 AK/SK/签名/模板齐全 → 走真实阿里云；
   配置缺失时自动降级为开发模式（不发短信也不报错）。

容器注入链路：`.env`（已 gitignore）→ docker-compose backend environment
（`GOCHAT_SMS_*` 已接上）→ `internal/config/config.go` 环境变量覆盖。
实测：`sendSmsCode` 返回 code=0，日志打印验证码，注册/登录走通。

> 安全说明：`configs/config.dev.toml` 含真实 AK，已被 .gitignore 忽略，勿提交版本库；
> 生产部署通过环境变量注入，不要在镜像/仓库里留密钥。

### 文件上传（本地磁盘存储，MinIO 为文档中的远期方向，未使用）

原实现：后端用**上传时的原始文件名**落盘、接口不返回路径；前端用本地文件名猜 URL。
导致：同名文件互相覆盖（演示时两人传同名图片头像互相串）、上传路径可预测、
文件名含 `../` 可目录穿越、三处"submit 后不等上传完成就发业务请求"的竞态。

修复：后端随机重命名落盘（时间戳+随机串+原扩展名）+ 扩展名白名单
（头像限图片；聊天文件限文档/图片/压缩包/音视频，拒绝 .html/.svg/.js 等可执行脚本）+
`filepath.Base` 防目录穿越 + 接口返回真实相对路径；前端统一用后端返回值拼 URL
（新增 `web/chat-server/src/utils/upload.js`），并改为"先上传拿路径、再提交业务请求"。
实测：上传返回 `/static/files/<随机名>.png`、静态可访问 200、`.html` 被拒、
`../evil.png` 未越界写出、文件消息 WS 收发正常。

## 五、演示时注意

- 手机/局域网访问：`http://<服务器IP>:8080`，前端自动指到同一 IP 的 8000；
  后端默认监听 0.0.0.0:8000 且 CORS/WS Origin 已放行 8080 端口任意 host。
- 注册/短信登录：查 `docker logs gochat-backend` 拿验证码（开发模式）。
- 需要真实短信：`.env` 置 `GOCHAT_SMS_DEV_MODE=false` 并确保 AK/签名/模板有效。
- 管理后台：用 is_admin=1 账号（admin）登录后，左下角"设置 → 管理员模式"。
