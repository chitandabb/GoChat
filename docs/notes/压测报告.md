## 2. 工具

自研 Go 压测客户端 `bench/`（入仓，`go run ./bench`），四个场景：

- `conn`：并发拨号（100 路波次限流，避免瞬时拨号击穿 listen backlog）+ 长连接保持 + 心跳；
- `chat`：单聊稳态流量，发送方打点、按内容匹配回显计算端到端延迟（发送 → 服务端回显），含相位抖动模拟真实到达分布；
- `group`：群聊风暴，成员全量连接后爆发发言，统计每成员送达分布；
- `slow`：慢客户端注入（建立连接但不读），验证慢连接治理与全局吞吐隔离。

测试用户 / 群直接写入数据库（绕过短信注册），WS 使用与后端同密钥本地签发的 Access Token（鉴权链路与线上一致）。

- 实际收到 **30100 次**（含 100 条欢迎消息），**送达率 100%**；
- 每成员送达 **301/301**（min=max=avg），零丢失、零误断；

## 6. 场景四：慢客户端注入

50 个正常客户端 + 1 个建立连接后**完全不读数据**的慢客户端：

- 攻击者向慢客户端连发 300 条消息；
- 慢客户端在 **0.31–0.49s 内被服务端判定并断开**（连续丢弃计数达到阈值）；
- 期间正常客户端互发消息 **100% 送达、0 异常断开**——单慢客户端不影响全局吞吐。

## 7. 缓存验证（Phase 4 前后）

### 7.1 接口延迟（进程内 HTTP 客户端，连接复用；接口：会话列表 / 联系人列表）

| 场景 | P50 | P95 | P99 |
| --- | --- | --- | --- |
| 冷缓存（每次请求前删 key，DB 回源） | 3.7ms | **4.8ms** | 5.5ms |
| 暖缓存（连续命中） | 1.6ms | **2.2ms** | 3.1ms |

P95 由 4.8ms 降至 2.2ms（**-54%**）。注：本机 MySQL 在 Docker Desktop 内，冷路径下限较高；
同机原生 MySQL 的冷路径基线会更低，但暖/冷相对收益不变。

### 7.2 缓存命中率（Redis INFO keyspace_hits/misses 差值法）

暖启动后连续 2023 次读操作：**命中率 99.75%**（仅 5 次 miss，均为启动回填）。

### 7.3 数据库查询量（MySQL general_log 实测）

| 场景 | 业务 SELECT 数 |
| --- | --- |
| 暖缓存 500 次请求 | **4 次**（登录 1 次 + 少量启动查询），命中路径 0 次 |
| 冷缓存 50 次请求（每次 miss） | ~50 次（每次回源 1 次） |

按 99.75% 命中率折算，**数据库查询量降低 90%+**。

### 7.4 写路径优化收益

消息写路径从"读改写（RMW）追加缓存"改为 Cache-Aside 失效删除（顺带修复了旧代码只更新单向缓存 key 的脏读问题），
单条消息在分发循环中的 Redis 开销由 ~1.3ms 降为 ~0.1ms；同时修复了"发送方积压消息只有等到下一条新消息才会被转发"
的突发丢消息缺陷（详见第 8 节）。

## 8. 压测过程中发现并修复的问题（可面试讲述）

1. **持锁发送 channel 导致全局死锁**：`SendClientToLogin/Logout/Transmit` 在持有 `sync.Mutex` 时阻塞发送，
   并发拨号超过缓冲容量后分发循环永远拿不到锁。修复：channel 本身线程安全，mutex 只保护 Clients map。
2. **上行积压"只有来新消息才排空"**：突发场景下 2/3 消息滞留连接级 SendTo 缓冲（300 条仅 101 条进入分发）。
   修复：每条连接增加独立 Flush goroutine，与是否来新消息无关地持续转发 SendTo → Transmit。
3. **Write goroutine 同步 UPDATE 状态导致慢客户端误杀**：每条推送同步一次 `UPDATE message SET status`（约 6.8ms），
   突发流量下 Write goroutine 被拖慢，触发慢客户端判定。修复：Sent 语义不变（已写入连接即 Sent），
   状态落库改为后台批量 UPDATE（64 条一批 / 100ms 兜底）。群风暴送达率 24.8% → 100%。
4. **GORM 逐条 SQL 日志阻塞高吞吐路径**：控制台 I/O 成为分发循环瓶颈。修复：生产静默日志。
5. **分发循环 panic 拖垮整个服务**：增加单次迭代 recover，单条消息处理异常不中断循环。
6. **连接池未配置**：默认 MaxIdleConns=2 导致请求间隙连接频繁重建（每次新建连接都触发 `SELECT DATABASE()`）。
   修复：MaxOpenConns=100 / MaxIdleConns=50 / ConnMaxLifetime=30min。

## 8b. Kafka 模式端到端验证与调优

环境：`docker compose up -d kafka`（apache/kafka 3.7，KRaft 单节点，1 分区），后端以
`CONFIG_FILE=configs/config.kafka.toml`（messageMode=kafka）运行。消息链路：
WS 客户端 → kafka-go Writer（分区键 = receiveId，保证单会话保序）→ broker → 消费组 `chat` → 分发循环 → 推送。

| 参数 | 默认 | 调优后 | 影响 |
| --- | --- | --- | --- |
| 生产者 BatchTimeout | 1s | 10ms | 低流量下消息不再在生产者缓冲等批（延迟主因） |
| 消费者 MaxWait（fetch 等待） | 10s | 100ms | 消费端拉取不再长时间挂起（长尾主因） |
| broker fetch.max.wait.ms | 500ms | 50ms | broker 侧批次等待上限 |

调优后 20 对单聊、600 条消息：**P50=20.3ms、P99=45.6ms、max=56.4ms，100% 送达、消费组 LAG=0、落库 600/600**。

> 口径说明：`messaging.md` 承诺的延迟指标以 channel 模式为准；Kafka 模式的价值在异步解耦、
> 削峰与崩溃恢复（未消费消息由 broker 保留，重复消费由 uuid 幂等去重），调优后延迟同样进入
> 同一数量级。

## 8c. 管理员禁用即时生效实测（简历条目 1"禁用用户即时撤销并断开"出处）

场景：普通用户 victim（`U_VICTIM_001`）登录并建立 WS 长连接保持在线；
管理员调用 `POST /api/v1/admin/disableUsers {"uuid_list":["U_VICTIM_001"]}`。

| 验证点 | 结果 |
| --- | --- |
| 在线 WS 连接即时断开 | 连接 20:23:42.986 建立，禁用调用后 **20:24:05.987 被服务端 TCP 层直接切断**（close 1006，无延迟等待） |
| Refresh Token 全量撤销 | 禁用后携原 refresh Cookie 调 `/api/v1/auth/refresh` → **40100「登录已过期，请重新登录」** |
| 重新登录被拒 | 禁用后重新登录 → **40000「该账号已被禁用，请联系管理员」** |
| 恢复 | `ableUsers` 启用后重新登录成功（code 0） |

链路（`user_info_service.go` `DisableUsers`）：置 `status=DISABLE` → `auth.RevokeAll(uuid)`
（清 Redis 白名单，全部 Refresh 失效）→ `chat.KickOut(uuid)`（在线表移除并关闭 TCP 连接）→
会话软删。WS 断开为 TCP 层立即关闭（1006），无需等待 close 帧握手，达到"即时生效"。

## 8e. Kafka 模式规模验证与容量边界（2026-08-15 追加）

8b 节原测 20 对单聊（600 条）。本节把规模提升到 100 对，并验证超容量行为。
**注意：本节为修复前基线（瓶颈表现），修复后最终数据见 8f 节；简历数字以 8f 节为准。**

**修复前 - 容量内（100 对 × 1 msg/s = 100 msg/s，60s）：**

| 指标 | 结果 |
| --- | --- |
| 发送 / 回显 | 5999 条发送，回显 100% 送达 |
| 端到端 P50 | **28.8ms** |
| 端到端 P99 | **104.8ms** |
| max | 142.1ms |
| 连接异常 | 0 |

**修复前 - 超容量（100 对 × 2 msg/s = 200 msg/s，60s）：**

| 指标 | 结果 |
| --- | --- |
| 发送 11924 条，回显仅 5045 条（42%） | 消费积压：测试结束时消费组 LAG=6496 |
| 端到端 P50 / P99 | 12.7s / 34.8s（退化为"排队等待 + 处理"，非故障） |

**修复前 - 容量边界分析**：Kafka 消费循环为单 goroutine 串行（`kafka_server.go`：`ReadMessage →
SendMessageToTransmit`），每条消息同步落库（本机 Docker Desktop MySQL 单条 INSERT ≈6.8ms），
故单实例消费吞吐上限 ≈ **147 msg/s**。100 msg/s 容量内延迟正常（P99 104.8ms，与 8b 节
20 对同数量级）；200 msg/s 超出上限后消息在 broker 积压，LAG 增长，延迟退化为排队时间，
但**消息不丢**（Kafka 持久化 + 消费组 offset + uuid 幂等，积压最终会消费完）。

> 意义：这给出了 Kafka 模式单实例的**真实容量边界**（≈147 msg/s，受落库延迟约束），
> 以及超限时的行为口径——积压不丢消息，与 channel 模式"有界缓冲 + 显式拒绝"形成对照：
> Kafka 模式是无限队列 + 延迟退化，channel 模式是有限队列 + 拒绝。两者共享同一套
> 投递语义（先落库后推送、慢客户端治理），简历口径仍以 channel 模式承诺延迟数字。

**测试隔离修正（bench 修复）**：原 chat 场景 content 用 `chat-{idx}-{seq}`，每轮从 seq=0
开始，上一轮未回显的 sentAt 条目会被本轮相同 content 的回显匹配到旧时间戳，虚高延迟
（修复前复测 P50=603ms 即此污染所致）。修复：每轮生成唯一 `runID` 前缀
（`chat-{runID}-{idx}-{seq}`）。本轮数据均为修复后复测结果。

## 8f. 批量落库优化与 Kafka 模式最终数据（2026-08-15）

**问题**：8e 节实测 Kafka 模式单实例消费上限 ≈147 msg/s（单 goroutine 串行落库，
Docker Desktop MySQL 单条 INSERT 6.8ms），200 msg/s 即积压（LAG 6496、P50 12.7s）。

**修复**（`internal/service/chat/kafka_server.go`）：消费端攒批落库，仿照
`status_updater.go` 的批量模式——单批 64 条或 10ms 刷盘（先到先触发），批量 INSERT
落库成功后经新增 `TransmitPersisted` 通道投递，由分发循环直接推送（跳过二次落库），
"先落库后推送"语义不变；批量失败（如含重复 uuid）回退逐条 INSERT 保持幂等。
**群聊不批量**：广播型负载串行落库天然限速，避免批量洪峰同时扇出打满每连接
SendBack 队列（压测实证：群消息批量会导致正常客户端被误判为慢客户端而丢弃推送）。

**修复后 - Kafka 模式最终实测（简历口径）：**

| 场景 | P50 | P99 | 送达率 | LAG |
| --- | --- | --- | --- | --- |
| 100 对 × 1 msg/s（100 msg/s） | **24.5ms** | **71ms** | 100% | 0 |
| 100 对 × 2 msg/s（200 msg/s） | 33ms | 316ms | 99.96%（5 条） | 0 |
| 250 对 × 2 msg/s（500 msg/s） | 39ms | 414ms | 100% | 0 |
| 500 对 × 2 msg/s（1000 msg/s） | 52ms | 290ms | 100% | 0 |

- 群风暴（100 人 × 10 发言 × 30 条，预期扇出 30000 次）：**每成员 301/301（100%），
  零丢失、零误断**，LAG=0；
- 慢客户端注入：被服务端判定断开，50 个正常客户端互发 100% 送达、0 异常断开；
- 3000 连接保持 300s：零掉线、goroutine 恒 3005、堆内存 GC 正常回收（32–46MB 波动）。

**结论：批量落库把 Kafka 模式单实例消费上限从 ≈147 msg/s 提升至 ≥1000 msg/s
（约 7 倍）；200 msg/s 超容量场景从"积压秒级"恢复为"百毫秒级"。**

> 已知行为（面试口径）：conn 场景结束瞬间 3000 连接同时断开，触发 Logout 通道积压 +
> 3000 次 MarkOffline 串行 DB 更新，紧接的下一轮压测会被短暂拖慢（实测 P50 秒级）；
> 真实场景连接随机断开不存在此风暴，且消息不丢（Kafka 持久化兜底）。

## 8g. 消费幂等修复：Kafka 重复消费不再重复落库（2026-08-15）

**缺陷复现**：消息 uuid 由服务端生成（客户端 `ChatMessageRequest` 不带 uuid），因此
Kafka 重复消费 / offset 回退时，服务端会为同一条消息生成**新 uuid**，uuid 唯一索引
拦不住——"消息 uuid 幂等"在 Kafka 模式下实际失效。实测：消费组 offset 重置到
earliest 重放 13438 条消息，DB 新增 **13412 行**（重复落库）、接收方重复推送。

**修复**（`kafka_server.go` `claimOnce`）：以 Kafka 消息的 **(topic, partition, offset)**
为幂等键，消费入口 Redis `SETNX` 原子认领（TTL 24h），认领失败即跳过（重复消费）。
幂等键写入失败时保守放行（宁可重复也不丢消息）。

**修复后验证**：同批 13438 条消息二次重放——**DB 零新增**，Redis 幂等键 13438 个
与消息数一一对应，全部命中跳过。`SETNX` 的原子性保证并发消费同一条消息时只有一个
通过，重复推送也随之消除。

## 8h. 离线补偿与连接清理闭环验证（2026-08-15）

**场景 A - 离线消息经历史拉取补齐**（"为什么敢丢推送"的立论根基）：

| 步骤 | 结果 |
| --- | --- |
| B 离线，A 发 3 条消息 | 3 条全部落库（先落库后推送，消息不丢） |
| B 上线拉取会话历史（`getMessageList`） | **3 条全部返回，补齐 100%** |

说明：离线期间消息不推送、不丢失；重连后由会话历史拉取兜底补偿，与"丢弃推送"
同一闭环（推送是加速通道，落库是事实）。

**场景 B - 半开连接清理**（心跳价值验证）：

建立 20 个 WS 连接后模拟底层 TCP 断开（无 WS 关闭帧，服务端只能靠读超时感知）：

| 时间点 | TCP 连接数（8000 端口 Established） |
| --- | --- |
| 建立后稳定 | 20 |
| 底层断开 2s | 20（服务端尚未感知） |
| 断开 65s（>PongWait 60s） | **0（全部清理）** |

说明：连接异常消失（网络黑洞/拔线）时，TCP 层无关闭帧可依赖，靠 Ping/Pong 心跳
读超时（PongWait=60s）判定半开连接并回收，避免僵尸连接堆积（在线表/句柄泄漏）。
实测 20 个半开连接在 65s 内全部被清理，回收路径（摘除在线表 + 记 last_offline_at +
关闭 channel）复用统一登出逻辑。

## 8i. 多分区 + 分区键保序验证，及两个真实缺陷修复（2026-08-15）

**背景**：`messaging.md` 承诺 Kafka 模式"以 receiveId 为分区键，保证同一会话/群的
消息进入同一分区保序"，但此前 topic 恒为 **1 分区**（`config.kafka.toml` `partition=1`），
分区键机制从未被真实考验。本轮把 `partition` 改为 **3**，删除 topic 与消费组重建后，
从两个层面验证：

**验证工具**（新增入仓）：

- `bench -mode order`：N 对单聊快速连发 burst 条消息（seq 递增），接收端与发送端
  回显分别断言 seq 严格递增、无乱序/重复/缺失，轮询等待收满（不再固定 sleep）；
- `test/kafka_ordercheck`：独立消费组全量消费 topic，输出每个 key(receiveId) 落到的
  分区集合、按 runID 分组的 seq 递增性、各分区消息数分布。

**实测结果**（topic 3 分区，含多轮测试累计 23010 条消息）：

| 检查项 | 结果 |
| --- | --- |
| key → 分区映射 | 50 个 key 全部恒定落在**单分区** ✓（无跨分区漂移） |
| 会话内 seq 递增 | 162 个会话轮全部严格递增 ✓（分区内 offset 顺序保持） |
| 分区分布 | 29.6% / 38.7% / 31.7%，均匀度 76%（Hash 分区负载分散） |
| 端到端 30 对 × 50 条 | 1500/1500 送达，接收端与回显双双零乱序（修复后） |
| 端到端 50 对 × 200 条 | 10000/10000 送达，零乱序零重复（修复后） |

**结论：分区键保序承诺实测成立**——同一会话消息经 Hash 分区键恒定落同一分区、
分区内 offset 严格有序、批量落库路径不破坏顺序、3 分区负载分散正常。

**过程中发现并修复的缺陷 1：topic 重建后幂等键误杀新消息**

- 现象：删除 topic 重建（offset 从 0 重新计数）后，partition 0 的 428 条新消息
  全部被"重复消费跳过"（后端日志刷屏），不落库不推送，仅 partition 1/2 正常。
- 根因：幂等键 `kafka_dedup:{topic}:{partition}:{offset}` 不含消息时间戳，旧 topic
  留下的键（TTL 24h）与新 topic 同号消息的键完全相同，SETNX 误判为重复。
- 修复：幂等键追加**消息时间戳**维度（Kafka 消息时间戳由 broker 持久化、重放不变，
  恰好区分"同一消息重放"与"新 topic 的同 offset 消息"）。
- 验证：重建后 10000 条新消息消费"重复消费跳过"= 0，全部正常落库。

**过程中发现并修复的缺陷 2：consumeLoop 尾部消息滞留（崩溃可丢消息）**

- 现象：30 对 × 50 条只落库 1497/1500，缺的 3 条恰是 partition 1 末尾
  （offset 4447/4448/4449）；幂等键已存在（claimOnce 通过）但 DB 无记录。
- 根因：`consumeLoop` 中 `ReadMessage`（阻塞调用）与 ticker flush 串行——消息流
  停止时 `ReadMessage` 阻塞在 fetch 上（kafka-go 内部循环等待），ticker 分支永远
  等不到执行，**最后一批（<64 条）消息无限期滞留内存**。更严重的是 kafka-go 的
  `ReadMessage` 返回消息即提交 offset（FetchMessage + Commit），若此刻进程崩溃，
  这批消息既不在 DB、offset 又已提交，**永久丢失**——批量落库把"落库"延迟到攒批
  窗口之后，但 offset 提交没有同步延迟，暴露窗口 = 批滞留时间（无限）。
- 修复：读取与攒批解耦——独立 Reader goroutine 产出消息到缓冲通道（通道满时阻塞
  形成天然反压），主循环 `select` 同时监听 ticker 与消息通道，无论消息流是否停止，
  ticker 都能按时触发 flush，滞留窗口收缩到 10ms 以内。
- 验证：同规模重跑 1500/1500 全落库、全送达、5s 内收满（修复前 30s 超时）；
  50 对 × 200 条 10000/10000 全送达零乱序（修复前仅 1154/10000 且 100 连接被误断）。

## 8j. 消费崩溃恢复：实测 PASS + 分析出"已认领未落库"窗口并封死（2026-08-15）

**场景**：消费端在任意时刻 `kill -9`（模拟崩溃），重启后验证不丢不重。

**实测（修复前）**：50 对 × 200 条发送中 kill 后端——消费组已读 2245 条（offset
已提交）、DB 已落库 2369 条（kafka-go 的 offset 提交异步滞后于落库）、重启后
124 条已落库未提交的消息被重放，**幂等键全部拦截，DB 最终 10000/10000 零丢失
零重复**。幂等机制在真实崩溃 + 重放场景下验证有效。

**但分析发现理论窗口（8j 修复的核心）**：`ReadMessage`（提交 offset）→
`claimOnce` 写幂等键（**落库前**）→ 攒批 → 批量 INSERT。若崩溃落在"已认领、
未落库"的窗口内（batch 滞留期或 INSERT 执行期），重启后重放该消息 → 幂等键
已存在 → 跳过 → **消息永久丢失**（offset 已提交、DB 没有、键拦住重放）。

**修复（双层防线）**：

1. **DB 层最终防线**：`message` 表新增 `kafka_key` 列 + 唯一索引（值为
   `topic:partition:offset:时间戳`，与 Redis 幂等键一致）。落库与去重原子化：
   无论 Redis 键如何，同一条 Kafka 消息在 DB 里只能有一行。channel 模式为
   NULL（MySQL 唯一索引允许多 NULL），不参与约束。Transmit 路径（群聊/文件/
   音视频）同样携带 kafka_key 落库（`TransmitData` 结构），由 DB 兜底。
2. **Redis 快速路径状态机**：幂等键值从"1"改为两态——`pending`（已认领，
   未完成）与 `done`（已落库）。`claimOnce` 写 pending；落库成功后置 done。
   重放时：`done` → 跳过；`pending` → 上次未完成（崩溃残留）→ **放行重试**，
   由 DB 唯一索引保证不重复落库。崩溃任意时刻：要么 done 跳过、要么 pending
   重试且 DB 兜底，**丢消息窗口彻底封死**（TTL 24h 过期后同样由 DB 兜底）。

**验证（全量重放 44510 条）**：

| 键状态 | 重放行为 | 实测 |
| --- | --- | --- |
| `done` | 跳过 | 零重复落库 ✓ |
| `"1"`（8g 旧格式） | 按 done 跳过（修复后） | 零新增 ✓ |
| `pending`（手动模拟崩溃残留） | 放行重试 + DB 索引兜底 | 重试日志 ✓ 不重复 ✓ 置回 done ✓ |

过程中还发现并修复一个**兼容性缺陷**：最初把旧格式键值 `"1"` 误当 pending
放行重试，导致全量重放 2 分钟产生 24604 个重复组（旧行 kafka_key 为 NULL，
DB 索引拦不住）。修复：`"1"` 等价于 done（8g 时代语义就是"已处理过"）。

**回归**：修复后正常链路 30 对 × 50 条 1500/1500 保序送达零重复，LAG=0。

## 8k. 双实例横向扩容：实测暴露"跨实例推送失效"与"已读未落库崩溃窗口"两个缺陷，逐一修复（2026-08-15）

**场景**：起两个后端实例（端口 8000/8001，同一消费组 `chat`、同一 DB/Redis），
验证 Kafka 3 分区在 2 个消费者间 rebalance 后，消息不丢不重、会话保序、端到端可达。

**实测一：rebalance 正常，消费可扩展**——3 分区自动分配（实例 A 持 1 个、
实例 B 持 2 个），落库完整、LAG=0、幂等键与 DB 唯一索引跨实例兜底正常。

**缺陷一（推送）**：所有客户端连实例 A，但 partition 0/2 由实例 B 消费——
B 落库后查**本地** Clients map 推送，用户连接在 A → 推送静默失败。
端到端仅 **650/1500**（恰为 A 持有分区的消息），对 0/对 2 收到 0/50
（再次印证同会话同分区）。消息不丢（落库 + 会话拉取兜底），但实时推送跨实例失效。

**修复一（推送事件广播）**：新增 `chat_push` topic——落库成功后把
`PersistedText`（请求 + 已落库消息）写回广播；每个实例用**独立消费组**
（进程唯一）消费全量推送事件，查本地 Clients map 命中才下发。
广播语义下一条推送事件被所有实例消费，但只有持有目标连接的实例真正推送
（miss 自然跳过）→ 跨实例送达、不重不漏。channel 模式不受影响（进程内直推）。
File/AV 消息的内联推送未改造（已知边界：多实例下仍限本实例，会话拉取兜底）。

**缺陷二（崩溃窗口，比 8j 更宽）**：发送中 `kill` 实例 B，最终落库
1432/1500，**丢 68 条**。根因：`ReadMessage` 返回即提交 offset，但消息要
经 msgCh（≤64）+ 攒批（10ms）才落库——崩溃在"已读未落库"区间：offset
已提交、幂等键未写（claim 在主循环才做）、DB 无记录 → 重启从已提交 offset
继续 → 这 68 条永久跳过。8j 只覆盖"已 claim 未落库"，未覆盖"已读未 claim"。

**修复二（manual commit）**：Reader goroutine 改用 `FetchMessage`（不自动
提交）+ 读出即 claimOnce（写 pending 键）；offset 提交延后到**落库成功**
（`CommitMessages`，批量路径整批提交、回退逐条对成功者提交、Transmit 路径
转发后提交）。语义变为"落库成功才算消费完成"：崩溃时已读未落库的消息
offset 未提交 → 重启/重平衡重放 → pending 重试 → 不丢；重放不重复由
幂等键 + DB 唯一索引兜底。

**验证（修复后）**：

| 场景 | 结果 |
| --- | --- |
| 双实例正常（30 对 × 50） | 1500/1500 全送达，零重复零乱序，LAG=0 |
| 双实例 + 发送中 kill 实例 B | 落库 **1500/1500**（修复前 1432），LAG=0，A 接管 B 分区 |
| 单实例回归（30 对 × 50） | 1500/1500 全送达，LAG=0 |

**延迟代价**：广播给推送增加一跳 Kafka 写 + 读（本地回环 ms 级），容量内
P99 变化见 8f 基线对比（本机实测收满时间 19-20s vs 修复前 4.5-12.5s，
含编译/双实例分摊开销，端到端量级一致）。

**已知边界（记录）**：File/AV 消息多实例下推送仍限本实例；广播放大倍数
= 实例数（事件量线性增长），大规模集群可换"在线表路由"方案（推送前查
用户所在实例精准转发），本项目 2-3 实例广播代价可忽略。

## 8l. 故障注入三连：MySQL 挂暴露"offset 带过"静默丢失缺陷并修复（2026-08-15）

**场景**：依次停掉 MySQL / Redis / Kafka，验证依赖故障期间消息不丢不重、恢复后自愈。

### MySQL 挂（核心缺陷）

**实测**：50 对 × 200 条发送中 `docker stop gochat-mysql` → 消费端批量落库失败，
offset 停滞（manual commit 生效，失败消息不提交）；恢复 MySQL 后重启后端重放
→ **9999/10000，丢 1 条**（`chat-r36875600-25-0`，幂等键停留在 pending）。

**根因（manual commit 的边界缺陷）**：Kafka 提交是**分区级单调**的——提交
offset N 即标记 0..N 全部已消费。MySQL 挂的瞬间，25-0（offset 16005）所在批
落库失败（键 pending、offset 未提交），但**同分区后续消息在 MySQL 半恢复时
成功落库并提交**（提交到 16257）→ 16005 被"带过"标记为已消费 → 重启重放
从 16257 开始 → 25-0 永久跳过。落库失败 ≠ offset 未提交，两者在"批内部分
失败 + 后续成功提交"时脱节。

**修复（分区失败水位）**：`failedOffsets` 按分区记账失败消息的 offset；
提交前检查——分区存在未成功消息时，**只允许提交"最早失败 offset 之前"的
位置**；失败消息重新入队重试（不丢、不依赖重放），重试成功后解除记账、
推进提交。跳过（done）消息的即时提交同样受水位保护。

**复测**：同场景重跑（发送中停 MySQL → 恢复 → 重启）→ **10000/10000 全部
落库，缺失 0、重复 0**（集合差精确验证），LAG=0。

### Redis 挂

**实测**：发送不中断（1500 条全部进入 Kafka）；消费端 `claimOnce` 写键失败
保守放行（日志 694 条"幂等键写入失败，放行"），消息照常落库但吞吐暴跌
（每次 Redis 操作等连接超时重试，挂期间仅落库 525 条）；恢复后 LAG 归零、
**最终 1500/1500 零丢失**（重复由 DB kafka_key 唯一索引兜底）。

### Kafka 挂

**实测**：停 15s 后端不崩溃（消费循环错误重试）；恢复后消费组自动重连、
LAG=0；恢复后正常跑 30 对 × 50 → **1500/1500 全送达**。

**结论**：三类依赖故障均不丢消息（MySQL 挂靠 manual commit + 分区水位、
Redis 挂靠保守放行 + DB 索引、Kafka 挂靠 broker 持久化 + 自动重连）；
恢复后全部自愈追平。

## 8m. 认领即记账 + 连续水位提交：封死"在途未落库"窗口（P0-2，2026-08-16）

**问题**：8l 的 failedOffsets 只覆盖"落库失败"的 offset；批量路径中消息
已认领（SETNX pending）但仍在 msgCh/批次里等待落库时，若同分区后续消息
先落库成功并提交，会把在途消息的 offset "带过"（带过 = 提交位置越过
未处理消息）——崩溃后重放跳过，永久丢失。

**修复**：
- **认领即记账**（`registerInFlight`）：Reader/claim 侧认领消息的瞬间，
  按分区登记 in-flight offset，分区提交水位被钳制在最早 in-flight 之前；
- **完成即解除**（`clearInFlight`）：落库成功/duplicate 后解除记账，分区
  无剩余在途时水位推进；
- **补提交**（`commitPending`）：被水位暂扣的已完成消息暂存 pendingCommits，
  由 ticker 驱动在水位推进后补提交，不再滞留。

**实测**：ORDER 场景重跑（重投闭环下 50 对 × 200 突发）10000/10000 全量
落库、缺失 0、重复 0；故障注入复测（MySQL 挂期间发送）恢复后 LAG 归零。
重试闭环（P0-1）：落库失败消息重新入队重试（显式拷贝 km，避免 Go 1.20
range 复用同一地址导致整队列指向同一消息——实测修复前 retryQueue 被同一
offset 刷屏、水位卡死），MySQL 恢复后自动追平。

### 最终复测（干净构建，同一台开发机，负载随用户应用波动）

| 场景 | 结果 |
| --- | --- |
| CHAT 100 对 × 10 msg/s（1000 msg/s）30s | 29434/29434 = 100%，0 丢失；P50=90.0ms，P99=984ms，max=1.21s |
| CHAT 100 对 × 1 msg/s（100 msg/s）30s | 3000/3000 = 100%，0 丢失；P50=60.9ms，P99=87.8ms，max=119ms |
| ORDER 50 对 × 200 突发 | 10000/10000 会话内严格保序，无乱序/重复/缺失 |
| GROUP 400 人 × 20 发言 × 50 条 | 400000/400000 = 100.00%；每成员 min=max=1000，零送达成员 0 |
| CONN 100 连接 15s | 100/100 成功，goroutine 恒定 105、堆内存 2.2MB 无增长 |
| SLOW 100 正常 + 1 慢客户端 × 1000 条 | 慢客户端 1.09s 被断开；正常客户端 1300/1300，0 异常断开 |

**环境说明**：MySQL/Redis/Kafka 均跑在本机 Docker Desktop（WSL），与
开发机用户应用共享 CPU/磁盘。CPU 满载（100%）时 Redis RTT 升至 ~2ms、
Docker 磁盘 I/O 恶化，曾出现成员被误判慢客户端（群测 99.57-99.99% 抖动）；
负载回落后同构建稳定 100.00%。本次管线整改（异步失效 + 管道化删除 +
批量提交）把分发路径与 Redis/Kafka 逐次往返解耦，满载下的退化窗口显著
收窄。压测结论以低负载稳定复现为准。
