# GoChat 消息管道与投递语义

## 文档状态

- 本文定义 IM 消息链路的投递语义、反压与降级策略、压测验收口径,是 M2 的核心设计。
- 现状:上行两级缓冲(Transmit → SendTo → 拒绝提示)已存在;下行 SendBack 满时会阻塞分发循环,无降级逻辑;压测数据不存在。
- 已确认的决策:消息状态保持 `Unsent/Sent` 两态(见 [`domain-and-state-machine.md`](domain-and-state-machine.md));下行降级策略为**丢弃推送 + 连续超限断开慢客户端**。
- channel 模式与 Kafka 模式必须满足同一套语义;压测数字只对 channel 模式承诺。

## 设计目标

- **不丢事实**:消息先落库,推送只是加速;任何丢弃只丢"本次推送",不丢消息。
- **单个慢客户端不拖垮全局**:分发循环永不因某个连接阻塞。
- **内存有界**:所有缓冲 channel 有固定容量,极端流量下行为是拒绝 / 丢弃 / 断开,而不是无界堆积。
- **行为可解释、可复现**:每条降级路径有计数与日志,压测能稳定触发并观测。

## 运行模型

每条连接三个执行体,服务器一个分发循环:

```text
[前端] ⇄ WebSocket
   Read goroutine  : 读帧 → (channel 模式)投递 Transmit / (kafka 模式)写 Kafka
   Write goroutine : 消费 SendBack → WriteMessage → 置 Sent
[Server select 循环] : Login / Logout / Transmit 三通道,串行处理
   Transmit 消息 → 校验 → 落库(Unsent) → 查在线表 → 写入接收方 SendBack
```

- 在线表:`Clients map[uuid]*Client`,登录 / 登出经 channel 串行修改,读路径加锁。
- 群聊:消息落库一条(`receive_id` 为群 uuid),遍历 `group_info.members` 对每个在线成员各自写入其 SendBack;离线成员靠拉取。
- 发送方回显:服务端把消息同时回推给发送方连接(前端不本地回显,以服务端回推为准),该行为在推送量估算与压测脚本中要计入(每条单聊消息实际产生 2 次推送)。
- gorilla/websocket 约束:同一连接的写只允许发生在 Write goroutine(含错误提示回写,M2 修正上行拒绝时直接 `WriteMessage` 的违例)。

## 投递语义

1. **先落库,后推送**:消息进入分发循环后先持久化为 `Unsent`,再尝试推送;落库失败即向发送方报错,不进入推送。
2. **`Sent` 的含义**:已成功写入接收方 WebSocket(`WriteMessage` 返回成功)。不代表对方已读,也不代表对方应用层已处理。
3. **离线 / 丢弃补偿**:接收方离线、推送被丢弃、连接中断等所有未送达情形,统一由**会话历史拉取**兜底——前端打开会话即拉全量历史,`Unsent` 消息随之可见。不引入客户端 ACK 与重推队列。
4. **顺序**:单会话内以落库顺序(自增 id)为准;推送顺序不做跨会话保证。
5. **幂等**:消息 `uuid` 唯一索引,重复投递(Kafka 重复消费等)以唯一键冲突去重。

## 上行链路与反压(现状保留,细节修正)

```text
Read 收到帧
  → Transmit 未满:先排空本连接 SendTo 积压,再投递本帧
  → Transmit 满:暂存本连接 SendTo(每连接独立缓冲,天然按发送方隔离)
  → SendTo 也满:拒绝本帧,经 Write goroutine 回复"发送失败,请稍后重试"
```

- 语义:上行过载时**拒绝新消息**而不是排队到内存耗尽;拒绝对用户可见,可重试。
- M2 修正:拒绝回写改走 SendBack(单写者约束);增加拒绝计数指标。

## 下行推送与降级(M2 新增,已确认)

```text
分发循环写接收方 SendBack:
  select 非阻塞写
    成功     → 正常路径
    缓冲满   → 丢弃本次推送(消息保持 Unsent),该连接 dropCount++
  dropCount 连续达到阈值(初值 8,压测后调参)
    → 判定慢客户端,服务端主动断开连接
    → 客户端重连后经会话拉取补齐,自愈闭环
  任一次成功写入 → dropCount 清零
```

- 分发循环从此**永不阻塞**:最坏路径是"计数 + 丢弃"或"发起断开",两者都是 O(1)。
- 断开动作只向 Logout 通道投递,由既有登出路径统一回收,避免分发循环内做连接清理。
- 面试叙事:为什么敢丢?——事实已落库,丢的是加速通道;为什么要断?——持续丢弃说明通道已失效,断开触发重连拉取,比僵尸连接更快恢复一致。

## 连接生命周期(M2 修正项)

- channel 的关闭权归属唯一:SendTo / SendBack 由**创建方(连接管理)**在两个 goroutine 都退出后关闭;现状 `ClientLogout` 先 `Conn.Close()` 再关 channel 存在竞态,按此规则重写。
- 断线(读错误 / 写错误 / 心跳超时)与主动登出收敛到同一条清理路径:摘除在线表 → 更新 `last_offline_at` → 回收 channel。
- M2 增加心跳(Ping/Pong + ReadDeadline),清理半开连接。

## Kafka 模式差异

- 上行:Read 直接写 Kafka(带确认),不经 Transmit/SendTo;过载表现为写超时报错,语义仍是"拒绝可见"。
- 下行:消费循环替代 select 循环,推送与降级逻辑与 channel 模式完全一致。
- 崩溃恢复:未消费消息由 Kafka 保留,消费侧以消息 `uuid` 幂等去重;不承诺多实例语义。

## 每条推送的状态写放大(记录,不承诺)

现状 Write goroutine 每推送一条消息同步执行一次 `UPDATE status`。压测若证明 DB 写成为瓶颈,再评估批量 / 异步化;在数据支撑前不做优化。

## 压测与验收(M2)

- 工具:自研 Go 压测客户端(可讲述:并发拨号、消息注入速率控制、端到端延迟打点)。
- 场景与目标:
  | 场景 | 指标 |
  | --- | --- |
  | 1000+ 并发连接稳定在线(心跳) | 连接成功率、内存曲线平稳 |
  | 单聊互发稳态流量 | 端到端 P50 / P99 延迟(目标 P99 < 50ms,以实测修正) |
  | 群聊风暴(大群集中发言) | 分发循环不阻塞、丢弃与断开计数符合预期 |
  | 慢客户端注入(人为不读) | 全局吞吐不受影响,慢连接被断开,重连后拉取补齐 |
- 产出:压测脚本入仓、结果与机器配置记录到 `docs/notes/`,简历数字全部以此为出处。
- 验收原则:所有降级路径必须被压测真实触发过至少一次,"没触发"不等于"能工作"。
