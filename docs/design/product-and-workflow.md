# GoChat 产品定位与业务流程

## 文档状态

- 本文定义 GoChat 的产品边界、用户角色、业务模块和分阶段交付骨架。
- 当前仓库已实现 IM 主体功能(账号、联系人、群组、会话、消息、音视频信令、管理后台)。
- 鉴权体系、密码加密、消息反压落地、AI 助手均为**目标能力**,尚未实现;本文不把它们描述成当前能力。
- 各阶段的详细工作内容与验收标准在 [`delivery-plan.md`](delivery-plan.md) 中单独定义。

## 产品定位

GoChat 是一个**单实例可运行、以工程质量展示为目标的仿微信即时通讯系统**,叠加一个轻量级 AI 助手。

它的第一用途是作为开发者从 Java 后端转型 Go 后端的实战载体与对外展示项目。因此产品取舍遵循一个原则:

> **深度优先于广度。** 不追求功能数量,新的投入只围绕四条主线:鉴权与账号安全、消息管道可靠性与性能、缓存策略、AI 助手集成。每条主线都要做到"经得起追问"的深度:有设计文档、有真实实现、有可复现的验证数据。

## 产品目标

- 提供完整的单聊 / 群聊即时通讯闭环:联系人关系、会话管理、多类型消息收发。
- 建立可信的账号体系:加密存储、无感续期的登录态、后端不信任前端传入的身份字段。
- 消息管道在高并发下行为可预期:有明确的投递语义、反压与降级策略,并有压测数据支撑。
- 高频读接口有清晰的缓存策略与一致性方案。
- 在聊天流中集成轻量级 AI 助手(联网搜索、文件总结、文本扩写),不侵入 IM 核心链路。

## 明确不做的事情

- **多端同步与消息漫游**:单账号单端在线,不做多设备消息一致性。
- **朋友圈类社交扩展**:不做动态、点赞、评论等非 IM 核心功能。
- **音视频质量优化**:仅保留现有 WebRTC 信令转发能力,不投入媒体质量、TURN 部署等方向。
- **多实例分布式部署**:目标形态是单实例;Kafka 消息模式保留为可切换的架构演示,不作为默认路径,不做消息分区、多实例会话路由。
- **前端改版**:Vue 3 前端仅做适配性修改,不做重构或深度学习投入。
- **RBAC / Keycloak 统一身份**:本期只做两角色扁平模型,企业级权限体系记为远期方向,不占用当前排期。

## 用户角色

### 普通用户

注册、登录、维护个人资料;管理联系人与群组;进行单聊、群聊与音视频通话;使用 AI 助手(目标能力)。

### 管理员

由 `user_info.is_admin` 标记。在普通用户能力之上,可通过管理后台禁用 / 启用 / 删除用户与群聊,并将其他用户设为管理员。

角色模型保持两角色扁平:鉴权上线后,`is_admin` 进入登录态凭据,管理接口由统一的管理员校验中间件保护;不引入角色表与权限表。

## 业务模块

### 账号与认证

- 现状:手机号 + 密码注册登录、阿里云短信验证码登录、资料查看与修改(用户自助注销暂无,删除账号是管理后台能力)。
- 目标:密码哈希存储、双 Token 登录态、统一鉴权中间件、在线 / 离线状态落地。

### 联系人体系

申请添加联系人(人或群),对方通过 / 拒绝 / 拉黑,删除联系人,黑名单管理。人与群的关系统一放在 `user_contact` 中维护。

### 群组

创建群聊、申请加群、退群、踢人、解散;群主身份由群记录维护,成员列表当前存于 `group_info.members` JSON 字段。

### 会话与消息

打开 / 关闭会话;文本、文件、图片、视频消息的收发与存储;音视频通话信令(offer / answer / candidate 经 WebSocket 转发);聊天窗口内的联系人列表(chatroom 接口)。消息先落库、再推送。

### 管理后台

用户与群聊的禁用、启用、删除,设置管理员。

### AI 助手(目标,M3)

基于 Eino 的轻量级助手:联网搜索、文件总结、文本扩写,以 SSE 流式输出,与 IM 消息推送结合。作为独立模块接入,不改动 IM 核心链路。

## 核心业务流程

### 注册与登录

1. 用户以手机号注册(密码或短信验证码),后端校验手机号唯一性后创建账号。
2. 登录成功后建立登录态(目标:签发双 Token),前端凭登录态建立 WebSocket 连接。
3. 目标:连接建立 / 断开时更新 `last_online_at` / `last_offline_at`。

### 添加联系人

1. 用户搜索目标用户或群,发起申请,写入 `contact_apply`。
2. 对方在申请列表中通过或拒绝;通过后双方 `user_contact` 建立正向关系,并自动开启会话能力。
3. 拉黑、删除、退群、踢出均表现为 `user_contact.status` 的状态迁移,详见 [`domain-and-state-machine.md`](domain-and-state-machine.md)。

### 消息收发

1. 发送方通过 WebSocket 将消息发给聊天服务器。
2. 服务器先将消息落库,再根据接收方在线状态推送;接收方不在线时,消息状态保持未送达,由上线后的会话拉取补齐。
3. 消息管道的投递语义、反压与降级策略详见 [`messaging.md`](messaging.md)。

### AI 助手(目标)

1. 用户在聊天窗口内触发助手请求。
2. 后端经 Eino 编排调用模型与工具,以 SSE 流式返回,最终结果进入会话消息流。

## 分阶段交付

> 每个阶段以可验证的纵向闭环为完成标准;详细验收标准见 [`delivery-plan.md`](delivery-plan.md)。

### M0:工程化基础

统一响应结构与错误码、`/api/v1` 路由分组、main 显式依赖装配、数据库迁移与事务约定。M0 不新增业务功能,是后续所有阶段的地基。

### M1:鉴权与账号安全

bcrypt 密码哈希、双 Token 登录态与无感续期、统一鉴权 / 管理员中间件、WebSocket 接入鉴权、手机号唯一约束、在线状态落地。

### M2:消息管道与性能

投递语义落地(先落库后推送、离线补偿)、反压与降级机制真正实现、压测取得真实并发与延迟数据、高频读接口缓存策略验证。

### M3:AI 助手

Eino Agent + Tool Use、SSE 流式输出、与 IM 消息流集成。
