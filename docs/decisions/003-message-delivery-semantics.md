# 003. 消息投递语义:先落库后推送、两态状态机、丢弃降级

## 决策

- 消息可靠性以 MySQL 为唯一事实来源:**先落库(Unsent)后推送**,`Sent` 仅表示已成功写入接收方 WebSocket;一切未送达情形由会话历史拉取兜底。
- 消息状态机保持 `Unsent → Sent` 两态,不引入送达(Delivered)与已读(Read)回执。
- 下行推送降级:接收方缓冲满时**丢弃本次推送并计数,连续超限判定慢客户端并主动断开**;分发循环永不阻塞。上行过载沿用"两级缓冲后拒绝新消息"的语义。

## 理由

- 推送通道是加速路径不是事实路径,因此"丢推送"不等于"丢消息";这使反压策略可以大胆丢弃而不牺牲可靠性。
- Delivered/Read 需要客户端 ACK 协议、前端改造与群聊按成员记录,复杂度与"深度优先"定位冲突;两态 + 拉取兜底已构成完整可讲述的投递语义。
- 断开慢客户端优于纯丢弃:持续丢弃说明通道已失效,断开触发重连拉取,自愈闭环比僵尸连接更快恢复一致;优于阻塞:单慢连接不再能拖垮全局分发。

## 后果

- 弱网用户体验为"断开重连后补齐",而非逐条重推;这是有意取舍。
- 所有降级路径必须可观测(计数 + 日志)且被压测真实触发过,否则 M2 不验收。
- channel 与 Kafka 两种消息模式必须满足同一套语义;压测数字只对 channel 模式承诺。
- 若未来做多端同步或已读回执,本决策重开并需引入 ACK 协议设计。
