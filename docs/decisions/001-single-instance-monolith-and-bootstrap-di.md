# 001. 单实例单体 + bootstrap 手动依赖注入

## 决策

GoChat 保持单实例单体架构:一个 Go 进程承担 HTTP API、WebSocket 聊天服务器、AI 模块三种运行角色,不拆分服务、不做多实例部署。Kafka 消息模式保留为可配置切换的架构演示,不承诺多实例语义。

依赖装配全量收口到 `internal/bootstrap`:M0 一次性消灭业务包的副作用 `init()` 与包级单例(`dao.GormDB`、`https_server.GE`、`chat.ChatServer`、`gorm.XxxService` 等),所有对象由 bootstrap 按序构造、显式注入,`main` 只持有装配结果并按逆序关闭。

## 理由

- 项目定位是"深度优先的工程质量展示",单实例可将全部投入集中在鉴权、消息管道、压测与 AI 四条主线,分布式带来的会话路由、消息分区问题与定位冲突。
- Go 不需要 DI 容器:一个组装根中的构造函数调用让对象所有权、启动失败与关闭顺序在普通代码中可见。选择全量改造而非渐进,是因为 M1 鉴权中间件需要干净的装配地基,两套装配风格共存的过渡成本高于一次改透。
- 接口只在真实外部边界(短信、LLM、未来对象存储)引入,不为每个 struct 机械配接口。

## 后果

- 业务包禁止副作用 `init()`;新增模块必须经 bootstrap 装配。
- 每个基础设施客户端有明确的构造与关闭位置;"进程退出清空 Redis 全库"的旧行为随之移除。
- 单元测试可以用替身依赖构造 service,无需全局状态。
- 若未来真的需要多实例,需先补会话路由与消息分区设计,本决策届时重开。
